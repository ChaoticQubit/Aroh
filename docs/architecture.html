High level: app engine, Supabase, server engine

The app engine owns data, UI and everything deterministic, and works offline. The server engine owns all AI work and holds the provider keys. Supabase connects them: auth, rows, vectors, files, live events and the scheduler.

Troupekit framework layers (published separately)

The framework is its own Cargo workspace in troupekit/, with no Aroh imports. Each layer depends only on the layers below it.

One model call, end to end

Taken from rig 0.47: the request is built without I/O, the transport is injected, and one decoder serves streaming and non-streaming replies. The middleware chain comes from AutoAgents.

Agent hierarchy

The orchestrator persona classifies a goal, picks a workflow and writes any persona the library is missing. Workflows are graphs: setup runs once per goal, and ongoing workflows run on triggers.

Data flows

Three flows cover most of the system: creating a goal, a step-mode tick on Vercel, and an offline log that leads to an adaptation.

Create a goal

sequenceDiagram
  participant U as You
  participant A as App engine
  participant S as Server engine
  participant D as Supabase
  participant M as Models and search
  U->>A: goal text, links, files
  A->>D: upload files to Storage
  A->>S: POST /goals (JWT)
  S->>D: insert goal, enqueue setup run
  S-->>A: 202 run_id
  loop each graph step
    S->>M: persona or tool call
    S->>D: checkpoint and run_events
    D-->>A: Realtime run_events
  end
  S->>D: pause at approval node
  D-->>A: proposal ready
  U->>A: approve plan
  A->>S: POST /runs/{id}/resume
  S->>D: write actions, trackers, plugin
  D-->>A: row sync to SQLite
Question cards from the intake interviewer pause the run the same way the approval does: the run waits at a human node until you answer.

Step-mode tick (Vercel)

sequenceDiagram
  participant C as pg_cron + pg_net
  participant H as Host adapter
  participant G as Graph runtime
  participant D as Postgres
  C->>H: POST /tick every minute (signed)
  H->>D: claim due job (SKIP LOCKED)
  H->>G: load checkpoint, run one step
  G->>D: save checkpoint, emit events
  G-->>H: next step or done
  H->>D: re-enqueue or finish
  Note over H,G: each request stays under 300 s
Enqueueing a job also fires a webhook, so new work starts at once instead of waiting for the next minute. Worker mode runs the same claim-and-step loop without the trigger.

Offline log to adaptation

sequenceDiagram
  participant U as You
  participant A as App engine
  participant D as Supabase
  participant S as Server engine
  participant P as APNs
  U->>A: log "skipped gym, ate pizza" (offline)
  A->>A: store raw entry in SQLite, queue parse job
  A->>D: sync when back online
  D->>S: job webhook
  S->>S: log intake persona maps entry to trackers
  S->>S: tracker rule crossed, adaptation analyst runs
  S->>D: proposal or auto-applied change
  S->>P: push "plan updated"
  P-->>U: notification
  D-->>A: row sync, Inbox card
Deterministic work (marking done, editing, the recurrence window, local reminders) never waits for the server.

Run lifecycle

Every graph run is a serializable state machine stored in Postgres, so a crash, a deploy or a 300-second request limit loses at most one step.

stateDiagram-v2
  [*] --> queued
  queued --> running: claimed
  running --> checkpointed: step done
  checkpointed --> running: next step
  checkpointed --> waiting_human: approval or question node
  checkpointed --> waiting_budget: limit reached
  waiting_human --> queued: you answer
  waiting_budget --> queued: you raise limit
  running --> failed: error after retries
  checkpointed --> done: end node
  done --> [*]
  failed --> [*]
A failed eval sends the step back for one repair round. If it fails again, the run moves to waiting_human with the reason.

Code rules

One copy of everything

  • Shared logic lives in one module (troupekit-core, aroh-domain, src/lib/ui) and is imported, never copied.
  • Before adding a helper, search for an existing one. Two call sites with the same logic move into the common module.
  • The UI reaches Rust only through src/lib/api. Components never call Tauri directly.
  • Plugin views are TOML trees that the renderer maps to components, so the UI stays replaceable.

How work lands

  • Each ticket starts with a Svelte mockup shown in an artifact. You approve it, then its code is ported, not rewritten.
  • One pod per feature: a PM plans and asks you, an engineer writes tests first, then code.
  • Tests run in Kiri containers. The leader takes a quick look and merges. No review tracks on this project.
  • Minimum code that works, with assertions on invariants and docstrings only, no comments.
